# 指标口径说明（SPEC）

本文是口径的唯一权威定义。代码实现与本文不符即为缺陷。

## 1. 时间与分区

- 事件时间戳一律以 UTC 存储（`ts_utc`，ISO 8601，形如 `2024-03-01T15:30:00Z`）。
- 分区字段 `dt` 取事件时间戳的 **UTC 日期**（`YYYY-MM-DD`），不得使用本地时区换算。
- 示例：`2024-03-01T23:30:00Z` 属于 `2024-03-01`；`2024-03-02T00:10:00Z` 属于 `2024-03-02`。

## 2. 幂等

- 同一 `event_id` 只允许存在一条有效记录。
- 在数据未变化的前提下，**重复执行加工任务，任何表的行数与汇总值都必须保持不变**。
- 全量重跑与增量重跑的最终结果必须一致。

## 3. 迟到数据

- 埋点存在上报延迟，事件的实际到达时间可能晚于其 `ts_utc`。
- 允许迟到窗口为 **24 小时**：只要事件的 `ts_utc` 落在已加工区间内，重新执行任务时必须能把它补进来，不得因为增量水位而丢弃。
- 迟到事件补入后，其所属 `dt` 分区的 DWS 指标必须同步更新。

## 4. 指标定义

### DAU（日活跃用户数）

- 口径：当日有任意事件的不同 **`user_id`** 数量。
- 同一 `user_id` 绑定多个邮箱时只计 1 人；用户名的字母大小写不区分。
- 不按 email 去重。

### 订单数

- 口径：当日 `event_type = 'order_paid'` 的事件条数（按 `event_id` 去重后）。

### GMV（成交总额）

- 口径：当日 `event_type = 'order_paid'` 的 `amount_cents` 之和。
- 单位是**分**，必须使用整数累加，**禁止使用浮点数**参与求和或中间计算。
- 输出到 `dws_daily.gmv_cents`，为整数。

## 5. 表结构约定

- `ods_events`：原始事件落地，`event_id` 唯一。
- `dwd_events`：清洗后的明细，一行一个 `event_id`，带 `dt` 分区。
- `dws_daily`：按 `dt` 汇总，一行一天，字段为 `dau`、`orders`、`gmv_cents`。

## 6. 验收方式

- 首次加工后，DWS 的每日指标与手工按本文口径计算的结果一致。
- 重复加工 2 次，各表行数与 DWS 指标完全不变。
- 补入一条 `ts_utc` 早于当前水位的迟到事件后重新加工，该事件出现在 `dwd_events` 中，且对应分区的 `dws_daily` 指标随之更新。
